# Pairing Invitation UX and Gateway Auth Design

## Context

The current gateway pairing flow is functionally useful but too manual for the
primary iOS experience. The iOS app asks for a demo server URL, identity, room
override, and pairing code on the main screen. The gateway then issues a
long-lived phone token, which the app stores in Keychain and uses as bearer auth.

The project direction is to communicate over a trusted private network, but that
does not remove the need for application-level trust. The private network limits
who can reach the gateway. Gateway auth decides which reachable clients may read
runtime data, request LiveKit join tokens, or reset local state.

The browser dashboard is a development-only UI. It should not define the product
onboarding model and should not share the iOS pairing UX.

## Goals

- Make iOS first-run pairing feel like accepting a gateway invitation, not
  manually assembling connection settings.
- Preserve the trusted-device model for iOS and any future privileged clients.
- Protect all sensitive gateway JSON APIs consistently.
- Keep the browser dashboard available for development without turning it into a
  first-class product client.
- Leave private-network-specific provisioning available as an advanced mode, not
  the default onboarding path.

## Non-Goals

- Multi-user accounts or hosted authentication.
- A device management UI.
- Token rotation UI.
- A hostile-network hardening effort.
- Replacing dashboard polling with SSE or WebSocket in the first pass.
- Removing the browser dashboard.

## Recommended User Experience

The main iOS path should use a gateway invitation:

1. The operator starts the gateway on the Mac, VM, or private-network host.
2. The gateway creates a short-lived one-time pairing invitation.
3. The CLI prints a QR code or deep link, plus a short fallback code for manual
   entry.
4. The iOS app offers one primary action: pair with a gateway.
5. The app scans the QR code or opens the deep link.
6. The app calls the gateway pairing endpoint and receives a long-lived device
   token.
7. The app stores the token in Keychain.
8. The main screen changes from setup controls to operational state: paired
   gateway, connection status, connect/disconnect, reset, and forget pairing.

Manual server URL, identity, room override, and code entry should move to an
Advanced or Debug area. They are useful during development but should not be the
default first-run path.

User-facing language should move from "enter pairing code" toward "scan gateway
invitation" or "pair with gateway". The code can keep `PairingStore` internally
until a later cleanup.

## Gateway Invitation Model

The existing pairing store can evolve without changing its core security shape:

- A command such as `line pair` or a new `line invite` creates one pending
  invitation.
- The pending invitation stores a hash of the bootstrap secret, creation time,
  expiry time, server URL, and gateway device ID.
- The printed QR/deep link includes the server URL, bootstrap code or secret,
  gateway device ID, and expiry time.
- The bootstrap secret is one-time and short-lived.
- `POST /api/pair` validates the bootstrap secret and creates a trusted iOS
  device credential.
- The trusted iOS credential is a long-lived bearer token stored only hashed in
  gateway state and in cleartext only in the iOS Keychain.

The existing manual pairing code can remain as the fallback representation of
the same invitation.

## Gateway Auth Model

All sensitive JSON APIs require authentication:

- `GET /api/token`
- `POST /api/reset`
- `GET /api/events`
- `GET /api/tasks`
- `GET /api/usage`
- `GET /api/agent-runs`

`POST /api/pair` remains unauthenticated at the bearer-token layer, but it only
succeeds with a valid one-time invitation secret.

Static dashboard assets may remain unauthenticated. Runtime JSON data must not.

The iOS app sends `Authorization: Bearer <device-token>` for privileged API
requests. If a previously paired app receives `401`, it should treat the token as
expired, revoked, or reset and offer to pair again.

## Development Dashboard Model

The browser dashboard is explicitly development-only:

- It does not use the iOS pairing invitation flow.
- It uses a separate dashboard token generated by the gateway for that server
  process.
- The gateway prints the dashboard token or a local dashboard URL containing it
  in the URL fragment.
- `clients/web/app.js` stores the token in memory or session storage and adds an
  auth header to all JSON API requests.
- If the dashboard has no token, it shows a small dev-login control instead of
  repeatedly polling unauthenticated APIs.

For local development, serving the dashboard on `127.0.0.1` is still the safe
default. When the gateway is bound to `0.0.0.0`, the dashboard token makes LAN or
private-network exposure less surprising. It is still not a hostile-network
security boundary.

Dashboard token and iOS device token should be separate credential types. A
dashboard token can read development runtime data and request browser testing
tokens, but it should not create a trusted phone.

## Private Network Provisioning

Private network deployments can add an advanced provisioned mode later:

- The operator configures a client token or service credential out-of-band.
- The private network ACL controls which devices can reach the gateway.
- The gateway still checks the application credential before serving privileged
  APIs.

This is useful for Tailscale, WireGuard, SSH tunnels, VMs, and managed
environments. It should not replace gateway invitation UX for first-run iOS use.

## Error Handling

- Expired invitation: iOS shows that the invitation expired and asks the user to
  scan a new one.
- Gateway unreachable: iOS keeps the stored token and shows reconnect or pair
  again actions.
- `401` after pairing: iOS treats the device token as revoked or reset and offers
  to pair again.
- Dashboard unauthorized: dashboard shows the dev-token input instead of
  continuing unauthenticated polling.
- Gateway bound to `0.0.0.0` without a visible dashboard token: gateway prints a
  clear warning and generates a token by default.

## Testing Plan

Gateway tests:

- Unauthenticated requests to every sensitive JSON API return `401`.
- A valid iOS device token can call the expected privileged APIs.
- A dashboard token can call development JSON APIs.
- A dashboard token cannot create a trusted phone.
- Pairing invitations are one-time and expire.
- Pairing state stores only hashes for bootstrap secrets and long-lived tokens.

Web dashboard tests:

- Dashboard fetch helpers attach the configured auth header.
- Dashboard shows a dev-token state when unauthorized.
- Dashboard connect uses the same auth mechanism as other JSON calls.

iOS tests, where practical:

- Successful invitation handling stores the returned device token in Keychain.
- `401` on a paired request moves the UI to a pair-again state.
- Manual setup fields remain available in Advanced or Debug.

## Implementation Notes

The first implementation can be staged:

1. Protect all sensitive gateway JSON APIs and add dashboard token support.
2. Update `app.js` to use dashboard auth.
3. Extend the pairing command output to print a gateway invitation payload.
4. Add QR/deep-link handling to iOS and move manual fields out of the main path.
5. Update README, iOS setup, server setup, and security docs.

The current web dashboard polling can remain for the first pass if every JSON
request carries auth. SSE or WebSocket with auth is a later optimization.
